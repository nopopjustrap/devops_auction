# Правила внесения изменений

Мы используем единый порядок для кода, тестов и документации.

## Порядок работы

1. Создаём issue с целью, ограничениями и проверяемыми критериями готовности.
2. Обновляем локальный `main` командой `git pull --ff-only`.
3. Создаём ветку от актуального `main`:
   `feature/<name>`, `fix/<name>` или `docs/<name>`.
4. Разделяем работу на небольшие осмысленные коммиты:
   `feat:`, `fix:`, `test:`, `docs:`, `chore:`.
5. Выполняем обязательную локальную проверку `make verify`.
6. Отправляем ветку и создаём Pull Request со ссылкой на issue.
7. Просматриваем diff, результаты проверок и соответствие критериям issue.
8. Сливаем Pull Request в `main`, повторно обновляем локальный `main` и
   выполняем `make verify`.

## Обязательные проверки

Перед каждым Pull Request и после разрешения конфликта выполняем:

```bash
make verify
```

Команда включает:

- статический анализ `ruff check app tests`;
- проверку форматирования `ruff format --check app tests`;
- SAST Bandit;
- все автоматические тесты pytest с отчётами и порогами покрытия;
- три целевые мутации.

Если меняется HTTP-контракт, дополнительно проверяем `/docs` и обновляем
`docs/api.md`. Если меняется схема SQLite, добавляем новую ревизию Alembic, обновляем
справочные `schema.sql`, `docs/data-model.md` и проверяем миграцию на новой
и существующей БД.

## Запрещённые действия

- прямые изменения и force-push в `main`;
- слияние Pull Request с неуспешными проверками;
- отключение или удаление теста ради успешного запуска;
- коммит файлов `.env`, `.venv`, локальных БД, cookie-файлов и кэшей;
- коммит паролей, токенов и других секретов;
- переписывание опубликованной истории `main`;
- перемещение или повторное использование опубликованного тега версии.

## Критерии приёмки изменения

Изменение готово к слиянию, когда:

- выполнены критерии связанного issue;
- код, тесты и документация согласованы между собой;
- добавлены тесты для нового поведения и ошибок;
- `make verify` завершается успешно;
- в diff отсутствуют секреты и локальные файлы;
- конфликтов с `main` нет;
- Pull Request просмотрен целиком.

## Разрешение конфликтов

Конфликт разрешаем в рабочей ветке. Подтягиваем `main`, вручную формируем
итоговое содержимое, удаляем маркеры `<<<<<<<`, `=======`, `>>>>>>>`,
фиксируем результат отдельным коммитом и снова выполняем `make verify`.

## Выпуск версии

Аннотированный тег создаём только на проверенном merge-коммите в `main`:

```bash
git tag -a v0.1.1 -m "Auction Service v0.1.1"
git push origin v0.1.1
```

## Обязательные проверки ЛР3

`make verify` последовательно выполняет pip check, Ruff, форматирование,
Bandit, полный pytest с отчётами и три целевые мутации. Миграции, восстановление
и новая функция обязательно проверяются полным набором, а не только выбранным
тестом. Порог branch-aware coverage — 85%, функционального покрытия FR — 40%.
Отчёты находятся в reports/ и генерируются заново, а не редактируются вручную.

Запрещено ради успешного результата:

- удалять тесты или добавлять skip/xfail (pytest завершает такой прогон ошибкой);
- снижать пороги, уменьшать список обязательных FR или убирать этап verify;
- добавлять noqa/nosec, исключения Bandit/Ruff/coverage без отдельного
  обоснования в PR и проверки изменений;
- отключать мутации или считать ошибку импорта обнаруженной мутацией;
- менять уже применённые миграции; изменения схемы оформляются новой ревизией.

Критические файлы: Makefile, requirements*, pyproject.toml, pytest.ini,
tests/, scripts/, migrations/, CONTRIBUTING.md. Их изменение выделяется в
описании PR с причиной, влиянием на проверки и результатом make verify.
Нужен отдельный просмотр diff этих файлов. Техническая защита main и
обязательные GitHub checks настраиваются в ЛР5; локальные правила не являются
серверным запретом обхода.

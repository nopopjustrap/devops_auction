# ЛР6. Continuous Delivery и проверка работающего релиза

## Реализация и границы результата

Для доставки выбран отдельный Linux staging-сервер с Docker Engine, Python 3.11+
и SSH. Основная база разработчика и окружение GitHub runner не являются staging.
Приложение доступно на сервере только по `127.0.0.1:18000`; для UI используется
SSH-туннель через административную учётную запись.

Ветка реализации: `feature/lr6-cd`. Задача: #15. Новая функция — публичный
`GET /version`, возвращающий версию приложения `0.3.0` и SHA исходников,
записанный в образ во время сборки. Переменные сервера не могут подменить SHA.
В локальном запуске без сборки образа revision равен `development`.

Подготовлены код доставки, CI-репетиция и инструкция. Фактическая доставка на
отдельный сервер не считается выполненной, пока сервер не подготовлен и workflow
`CD staging` не завершится успешно. Адрес и доступ к такому серверу ещё нужны.

## Как проходит выпуск

1. Задача → ветка → локальный `make verify` → PR и согласование критических файлов.
2. CI выполняет проверки, собирает образ и проверяет его, включая репетицию доставки.
3. После слияния в main CI публикует проверенный образ `sha-<40-символьный SHA>`.
4. Workflow `CD staging` получает событие завершения CI. Он принимает только
   успешный запуск `push` в main этого репозитория, дополнительно проверяя
   успешность job `publish`. Старый автоматический запуск при сдвиге main отклоняется.
5. GitHub Environment `staging` выдаёт OAuth-реквизиты Tailscale и SSH-ключ отдельной
   учётной записи. После проверки публикации runner подключается к закрытой сети
   как временное устройство с тегом `tag:auction-ci`. Ошибка подключения блокирует SSH.
6. На сервер передаются только два проверочных Python-скрипта. Исходники приложения
   и Dockerfile на сервер не передаются; сборка там отсутствует.
7. Сервер выполняет `docker pull`, проверяет label revision и получает registry
   digest. Все последующие контейнеры запускаются по этому digest.
8. Предыдущий контейнер останавливается. Из его БД делается согласованная SQLite
   копия в новый Docker volume. Для первого выпуска создаётся новая БД.
9. В новом volume запускаются миграции и при необходимости создаётся первый
   staging-оператор. Существующий пароль оператора не сбрасывается.
10. Запускается новый контейнер. Проверяются Docker health, HTTP health/ready,
    revision и пользовательский сценарий. Только затем обновляется `state.json`.

Это учебное окружение с коротким периодом недоступности: во время остановки,
копирования и приёмки пользовательская работа не ведётся. Порт не открыт в Интернет.

## Приёмка работающей версии

`scripts/release_check.py` выполняет реальные HTTP-запросы к запущенному приложению:

- `/health` и `/ready`: ожидаемые статус и JSON;
- `/version`: точное совпадение revision с SHA выбранного тега;
- вход отдельным staging-оператором и проверка `/api/v1/auth/me`;
- создание уникальных продавца и покупателя;
- создание аукциона с комиссией 5%, лота с начальной ценой 100.00;
- открытие аукциона и продажа за 150.25;
- проверка комиссии 7.51, выплаты продавцу 142.74 и отчёта о выручке;
- закрытие аукциона и выход из сессии.

Проверочные записи имеют префикс `lr6-` и остаются в изолированной staging-БД как
свидетельство операции. Проверка не удаляет пользовательские данные и не подходит
для запуска на production без отдельной модели синтетических данных.

## Ошибка и откат

Неверный тег, недоступный registry и неполная конфигурация обнаруживаются до
остановки работающей версии. После остановки любой сбой миграции/запуска/приёмки
вызывает возврат старого контейнера и повторную проверку его работоспособности.
Несмотря на восстановление старой версии, команда завершается кодом 1, а CD — красным:
неудачная новая версия не объявляется успешным релизом.

Ручной `rollback` запускает предыдущий сохранённый контейнер с его собственным
volume и настройками. Он не требует registry. Это **откат кода и снимка данных**:
изменения, внесённые после прошлого выпуска, в старом снимке отсутствуют. Новая БД
остаётся в отдельном volume для анализа/ручного переноса. Такой подход допустим
для этого staging; переносить его на production без стратегии совместимости схем
и сохранения новых записей нельзя.

Контейнеры, образы и volumes не удаляются автоматически. Не выполнять `docker system
prune --volumes`: без сохранённых ресурсов офлайн-откат невозможен. Очистка старых
релизов допустима отдельно, с сохранением current/previous и нужных данных.

При обрыве SSH/runner во время операции остаётся `pending.json`. Следующий deploy
блокируется. Ручная операция `recover` возвращает последнюю принятую версию из
`state.json` и проверяет её. При первом неудачном выпуске предыдущей версии нет.

Одновременные изменения ограничены на двух уровнях: concurrency group
`auction-staging-delivery` с `cancel-in-progress: false` в GitHub и неблокирующий
`flock` на сервере. Второй ручной запуск на том же сервере тоже получает отказ.

## Подготовка сервера владельцем

Нужна отдельная тестовая ВМ с Docker Engine, Python 3.11+, SSH и исходящим HTTPS
к GHCR и Tailscale. В выбранной схеме ВМ находится за NAT VirtualBox; GitHub-hosted
runner подключается к ней через Tailscale. Публичный SSH и проброс на домашнем
роутере не требуются. Docker устанавливается по официальной инструкции
для ОС сервера: https://docs.docker.com/engine/install/.

На сервере администратор выполняет скрипт из проверенной версии репозитория:

```bash
sudo sh deploy/bootstrap.sh
```

Создаётся пользователь `auction-deploy`, каталог `/opt/auction-staging` и членство
в группе docker. Членство в docker фактически даёт управление всем хостом, поэтому
используется отдельная ВМ без рабочих данных. CI не получает root SSH-ключ или sudo.

### Сеть VirtualBox и Tailscale

Административный доступ с Windows: NAT-правило VirtualBox
`127.0.0.1:2222` → гостевой порт `22`, затем
`ssh -p 2222 <пользователь-Ubuntu>@127.0.0.1`. Это локальный доступ, он не делает ВМ
доступной для GitHub Actions. ВМ и Windows должны оставаться включёнными при выпуске.

На ВМ установить Tailscale из официального репозитория Ubuntu 26.04:
https://pkgs.tailscale.com/stable/#ubuntu-resolute.
Подключить ВМ к отдельной личной сети для лабораторной:

```bash
sudo systemctl enable --now tailscaled
sudo tailscale up --hostname=auction-staging --accept-dns=false
tailscale ip -4
```

Авторизацию по выданной ссылке выполнить в браузере. В Tailscale → Access controls
перенести `deploy/tailscale-policy.json` для этой отдельной сети. В существующей сети
с другими устройствами правила нужно объединять осознанно, а не заменять весь файл.
Политика разрешает только TCP/22 от `tag:auction-ci` к `tag:auction-staging`.
Сохранённые policy tests запрещают случайно открыть runner порты 80, 443 и 18000.
Широкое исходное правило «все ко всем» нужно убрать: разрешения складываются.
Оно также приведёт к падению этих отрицательных policy tests.

После сохранения политики назначить серверу тег:

```bash
sudo tailscale up --hostname=auction-staging --accept-dns=false \
  --advertise-tags=tag:auction-staging
tailscale status
```

Параметр `--advertise-tags` относится к `tailscale up`, а не к `tailscale set`.
В команде сохранены ранее заданные hostname и accept-dns. Если появится ссылка
повторной авторизации, открыть её в браузере и подтвердить устройство.

В Tailscale → Settings → Trust credentials (в старом интерфейсе OAuth clients)
создать OAuth credential с правом **Auth Keys: Write** (`auth_keys`) и только тегом
`tag:auction-ci`. Сохранить Client ID и Client secret непосредственно в секретах
GitHub Environment `staging`: `TS_OAUTH_CLIENT_ID`, `TS_OAUTH_SECRET`.
Клиенту не выдавать права изменения access policy или тег сервера.
Secret показывается при создании один раз; не передавать его в чат или Git.

`STAGING_HOST` — адрес из `tailscale ip -4`, `STAGING_PORT_SSH=22`.
`127.0.0.1:2222` используется только администратором на Windows.
Workflow использует закреплённый commit `tailscale/github-action` v4 и клиент
1.104.1, ждёт доступности узла и удаляет временный runner из сети при завершении.
Используется обычный OpenSSH с отдельным ключом: Tailscale SSH включать не нужно.
Политика в репозитории является шаблоном; её фактическое применение проверяется
отдельно в консоли Tailscale и при первом серверном выпуске.

Официальные инструкции:
https://tailscale.com/docs/integrations/github/github-action,
https://tailscale.com/docs/features/oauth-clients.

### SSH-ключ и конфигурация приложения

На своём компьютере создать отдельный ключ именно для staging:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/auction-staging-ci -C auction-staging-ci
```

Для неинтерактивного CI ключ создаётся без passphrase и хранится как GitHub secret.
Публичный ключ (`.pub`) установить в
`/home/auction-deploy/.ssh/authorized_keys`, добавив перед ним `restrict `:

```text
restrict ssh-ed25519 <публичная-часть> auction-staging-ci
```

Владелец файла — auction-deploy, права 600. `restrict` запрещает туннели/PTY этим
ключом; обычное выполнение команд и SCP остаются доступны. Туннель UI делается
своей административной учётной записью, не CI-ключом.

На сервере создать конфигурацию:

```bash
sudo install -m 600 -o auction-deploy -g auction-deploy \
  deploy/staging.env.example /opt/auction-staging/staging.env
sudo -u auction-deploy nano /opt/auction-staging/staging.env
```

Заполнить SMOKE_PASSWORD случайным паролем (например, результатом `openssl rand -hex 24`).
Остальные обязательные переменные уже показаны в примере. Формат — буквальные
`KEY=value`, без кавычек, export и подстановок оболочки. Файл не коммитить.

Если пакет GHCR приватный, под пользователем auction-deploy один раз выполнить
`docker login ghcr.io` с отдельным токеном только для чтения пакета. Вводить токен
интерактивно либо через `--password-stdin`; не вставлять его в команды, Git или чат.
Проверить `docker pull ghcr.io/nopopjustrap/devops_auction:sha-<опубликованный-SHA>`.
Для публичного пакета логин для чтения не нужен.

Проверить отпечаток SSH-хоста на сервере:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

На своём компьютере получить known_hosts через `ssh-keyscan -p <порт> <хост>` и
сверить отпечаток с полученным на сервере. Не доверять результату scan без сверки.

## GitHub Environment и секреты

Settings → Environments → создать `staging`:

- Deployment branches and tags: Selected branches and tags → только `main`;
- при необходимости Required reviewers (тогда автоматический запуск ждёт одобрения);
- Environment variables: STAGING_HOST, STAGING_USER=`auction-deploy`, STAGING_PORT_SSH=`22`
  или фактический порт;
- Environment secrets: STAGING_SSH_KEY — содержимое отдельного приватного ключа;
  STAGING_KNOWN_HOSTS — проверенная строка known_hosts;
  TS_OAUTH_CLIENT_ID и TS_OAUTH_SECRET — OAuth-клиент с тегом `tag:auction-ci`.

Приватный ключ и registry-токен в переписку не передаются. Pipeline использует
StrictHostKeyChecking=yes, а не автоматическое доверие новому SSH-хосту.

Для текущей ветки всё ещё требуется независимый CODEOWNER. Не отключать проверки
main для слияния этой работы. Конфигурация CD и скрипты входят в критические файлы.

После настройки сервера/Environment и успешного CI можно согласовать и слить PR.
Публикация main автоматически запустит `CD staging`. В первый раз предыдущего
релиза ещё нет. Для полноценного доказательства отката нужен второй успешный выпуск
0.3.x с другим SHA: версия ЛР5 0.2.0 не имеет /version и не проходит новую приёмку.

## Ручные операции

### Сквозной выпуск 0.3.1: версия в UI

Задача [#18](https://github.com/nopopjustrap/devops_auction/issues/18)
реализована в ветке `feature/lr6-release-version-ui`: страница входа и панель
оператора получают версию и короткий commit SHA из того же источника, что
`/version`. Полный SHA доступен в подсказке. HTML возвращается с `Cache-Control:
no-store`, чтобы обновление страницы после выпуска или отката показало текущую
версию. Локальный запуск без метаданных образа показывает `development`.

Исходный релиз 0.3.0 (`ae18edfb4f4de7f070e84583282efb6d6b37c89a`)
принят на отдельной ВМ 17.10.2026:
[CD, попытка 3](https://github.com/nopopjustrap/devops_auction/actions/runs/39063622696/attempts/3).
Отчет содержит `status=accepted` и успешный сценарий продажи.

Следующие действия выполняются после независимого согласования PR и успешного CI:

1. Слить изменение в main и дождаться успешного автоматического CD.
2. Обновить UI, проверить версию 0.3.1 и сравнить SHA с `/version` и main.
3. Запустить CD вручную с action=deploy и несуществующим тегом
   `sha-0000000000000000000000000000000000000000`. Ожидается отказ проверки
   опубликованного main-образа до обращения к ВМ. Работающая версия сохраняется.
4. Запустить action=rollback без tag. Ожидается повторная приемка версии 0.3.0
   с исходным SHA. Старая версия UI еще содержит прежнюю статическую подпись,
   поэтому результат отката проверяется по `/version` и отчету CD.
5. При необходимости вернуть 0.3.1 через action=deploy с полным SHA-тегом ее
   успешной публикации. Приемка выполняется заново.

Неверный тег демонстрирует отказ до развертывания. Отказы уже запущенного
контейнера и бизнес-сценария отдельно демонстрируются в `delivery-check`.
Откат возвращает также сохраненный том БД предыдущего релиза: новые данные
остаются в томе отмененной версии и не переносятся в старую автоматически.

### Запуск workflow вручную

GitHub → Actions → CD staging → Run workflow → branch `main`:

- action=deploy, tag=`sha-<полный SHA>`: доставить конкретный ранее успешно
  опубликованный CI коммит main;
- action=rollback, tag пустой: вернуть предыдущий принятый релиз;
- action=recover, tag пустой: восстановиться после прерванной операции.

При rollback/recover тег запрещён, чтобы не возникало неоднозначности.
Для deploy недостаточно существования тега: workflow требует успешный CI publish
этого SHA. Предыдущие CI-запуски должны оставаться доступны для этой проверки.

После выпуска смотреть журнал job deploy-and-accept, артефакт staging-delivery,
на сервере `/opt/auction-staging/last-result.json` и `state.json`. Конфигурационные
файлы и пароли в артефакты не включаются.

Для UI со своего компьютера:

```bash
ssh -L 18000:127.0.0.1:18000 <администратор>@<сервер>
```

Открыть http://127.0.0.1:18000 и http://127.0.0.1:18000/version.

## Репетиция всех отказов

Локально после `make setup` (нужны Docker и свободные loopback-порты):

```bash
make container-build
make delivery-check
```

Этот же target обязателен в CI перед ci-gate/publish. Создаётся временный локальный
registry, временное staging-окружение и четыре тестовых образа. Они производятся
только на runner для моделирования дефектов; на целевом сервере сборки нет.

Проверяются первый успешный выпуск, несуществующий SHA-тег, пропуск обязательной
переменной, неисправный healthcheck, сломанная продажа при работающих health/ready,
остановленный registry, второй успешный выпуск и ручной возврат первого при
отключённом registry. После каждого отказа дополнительно проверяется работа старой
версии по HTTP. Ресурсы репетиции удаляются по точным именам; чужие volumes и
контейнеры не трогаются. Отчёт: `reports/delivery-rehearsal.json`.

На защите открыть CI job delivery-check и отчёт: это доказательство проверенных
сценариев на Docker, но оно не заменяет отдельный реальный staging. Для доказательства
доставки показать успешный CD run, SSH/контейнер на целевой ВМ, /version и сценарий
продажи. Для ручного отката выполнить workflow rollback после второго принятого
релиза и показать возврат предыдущего SHA и успешную повторную приёмку.

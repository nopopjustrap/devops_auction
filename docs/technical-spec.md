# Техническое задание

Документ составлен по структуре ГОСТ 34.602-2020 для учебной
автоматизированной системы «Auction Service».

## 1. Общие сведения

Полное наименование: система управления аукционами «Auction Service».

Версия результата ЛР1: `v0.1.1`.

Основание разработки: задание на создание работоспособного приложения с HTTP
API, реляционной базой данных, веб-интерфейсом, аутентификацией и оформленным
Git-процессом.

## 2. Назначение и цели

Система предназначена для операционного учёта аукционов: регистрации
участников, подготовки лотов, проведения торгов, фиксации продаж и расчёта
выручки.

Цели:

- хранить связанные данные в единой реляционной модели;
- соблюдать статусы аукциона и лота;
- исключать некорректные и повторные продажи;
- предоставлять одинаковые функции через веб-интерфейс и HTTP API;
- ограничивать бизнес-операции аутентифицированной сессией;
- обеспечивать воспроизводимую проверку качества.

## 3. Характеристика объекта автоматизации

Основной пользователь — оператор аукциона. Он создаёт продавцов, покупателей,
аукционы и лоты, меняет статус торгов, регистрирует продажу и получает отчёт.

Системный администратор задаёт переменные окружения, запускает приложение,
создаёт схему SQLite и контролирует служебные адреса.

Основные сценарии:

1. При первом запуске создаётся учётная запись оператора.
2. Оператор входит в систему.
3. Оператор регистрирует продавца и покупателя.
4. Оператор создаёт аукцион в статусе `DRAFT`.
5. В черновик аукциона добавляется лот продавца.
6. Аукцион с хотя бы одним лотом переводится в `OPEN`.
7. Доступный лот продаётся активному покупателю.
8. Оператор получает отчёт и закрывает аукцион.
9. Оператор завершает сессию.

## 4. Требования к системе

### 4.1. Функциональные требования

| Код | Требование |
| --- | --- |
| FR-01 | Система разрешает однократную регистрацию первого оператора. |
| FR-02 | Система выполняет вход по имени и паролю и создаёт серверную сессию. |
| FR-03 | Система выполняет выход и аннулирует текущую сессию. |
| FR-04 | Неаутентифицированный запрос к бизнес-API получает `401`. |
| FR-05 | Оператор создаёт и получает продавцов и покупателей. |
| FR-06 | Оператор создаёт и получает аукционы. |
| FR-07 | Оператор добавляет и просматривает лоты аукциона. |
| FR-08 | Оператор открывает и закрывает аукцион с проверкой статуса. |
| FR-09 | Оператор регистрирует продажу доступного лота. |
| FR-10 | Оператор получает число продаж и общую выручку. |
| FR-11 | Веб-интерфейс поддерживает полный основной сценарий. |
| FR-12 | `/health` и `/ready` отражают работоспособность сервиса. |
| FR-13 | OpenAPI описывает маршруты, модели и cookie-аутентификацию. |

### 4.2. Правила предметной области

- новый аукцион получает статус `DRAFT`;
- лот добавляется только в аукцион `DRAFT`;
- аукцион без лотов нельзя открыть;
- при открытии лоты `DRAFT` становятся `AVAILABLE`;
- продажа разрешена только в открытом аукционе;
- продать можно только лот `AVAILABLE`;
- покупатель и продавец должны быть активны;
- итоговая цена не может быть ниже стартовой;
- один лот имеет не более одной продажи;
- при закрытии непроданные лоты становятся `UNSOLD`.

### 4.3. Требования к данным

Реляционная БД содержит сущности `users`, `sessions`, `sellers`,
`buyers`, `auctions`, `lots`, `sales`. Связность обеспечивается
внешними ключами. Денежные значения хранятся в копейках как целые числа.
Исполняемая схема находится в `schema.sql`.

### 4.4. Требования к безопасности

- пароль хранится только как salted PBKDF2-хеш;
- токен сессии создаётся криптографическим генератором;
- в БД хранится только SHA-256-хеш токена;
- cookie имеет атрибуты `HttpOnly` и `SameSite=Lax`;
- в HTTPS-окружении включается `COOKIE_SECURE=true`;
- первая регистрация закрывается после создания оператора;
- секреты, локальная БД и cookie-файлы не входят в Git.

### 4.5. Требования к надёжности

- схема создаётся идемпотентно через `CREATE TABLE IF NOT EXISTS`;
- внешние ключи SQLite включаются для каждого соединения;
- продажа и смена статуса лота выполняются транзакционно;
- `BEGIN IMMEDIATE` защищает лот от конкурентной двойной продажи;
- ожидаемые ошибки возвращаются в едином JSON-формате;
- готовность БД проверяется маршрутом `/ready`.

### 4.6. Требования к интерфейсу

Веб-интерфейс работает в современном браузере без сборщика и сторонних
JavaScript-фреймворков. Он адаптируется к ширине экрана, содержит формы всех
основных операций, отображает ответы и ошибки API и автоматически использует
сессионную cookie.

### 4.7. Требования к программным средствам

- Python 3.12;
- FastAPI и Uvicorn;
- SQLite через стандартный модуль `sqlite3`;
- HTML, CSS и JavaScript;
- pytest и Ruff для проверки.

Конфигурация передаётся переменными `APP_NAME`, `DATABASE_PATH`,
`SESSION_TTL_HOURS`, `COOKIE_SECURE`.

## 6. Порядок контроля и приёмки

Результат принимается при одновременном выполнении условий:

- приложение запускается командами из README;
- первая регистрация, вход, защищённая операция и выход работают;
- основной сценарий выполняется через веб-интерфейс;
- некорректные запросы возвращают документированные коды;
- `make verify` завершается без ошибок;
- Swagger/OpenAPI соответствует фактическим маршрутам;
- локальные файлы и секреты отсутствуют в Git;
- изменения прошли issue, рабочую ветку и Pull Request;
- версия отмечена аннотированным тегом.

## 7. Подготовка объекта автоматизации

Перед запуском создаём `.env` из `.env.example`, устанавливаем зависимости
через `make setup`, создаём схему командой `make migrate` и проверяем проект
командой `make verify`. Первый оператор создаётся через корневую
веб-страницу.

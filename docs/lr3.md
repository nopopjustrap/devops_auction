# ЛР3. Отчёт о выполненной работе

В ходе лабораторной работы Auction Service v0.1.1 был дополнен автоматическими
проверками, миграциями базы данных, резервным копированием и восстановлением.
В качестве нового функционального изменения реализована комиссия аукциона.
Версия приложения повышена до 0.2.0.

Работа выполнена в рамках [задачи #7](https://github.com/nopopjustrap/devops_auction/issues/7)
в ветке `feature/lr3-verification-migrations-backup`. Изменения представлены в
[PR #8](https://github.com/nopopjustrap/devops_auction/pull/8).
Проверки проведены в изолированном окружении Linux x86_64 с Python 3.12.14.
Рабочая база данных и сервер пользователя в проверках не использовались.

## 1. Подготовка воспроизводимого окружения

Для установки проекта с зафиксированными зависимостями выполнена команда:

```bash
make setup
```

В результате создано виртуальное окружение `.venv`, установлены зависимости
из requirements-файлов и выполнена проверка их совместимости. Точные версии,
включая транзитивные зависимости, зафиксированы в `requirements.lock`.
Скрипт `scripts/setup.sh` также создаёт `.env`, если файл отсутствует, и задаёт
ему права 0600. Существующая конфигурация при повторном запуске сохраняется.

Воспроизводимость проверена в отдельной чистой копии проекта командами:

```bash
make setup
make verify
```

Чистая установка и полный набор проверок завершились успешно: пройдено
74 теста, совместное покрытие строк и ветвей составило 94,78% при пороге 85%.
Подготовка окружения не изменяла схему и данные рабочей БД.

Для типовых операций в Makefile добавлены единые команды:

| Команда | Реализованное назначение |
| --- | --- |
| `make setup` | Подготовка виртуального окружения и зависимостей |
| `make run` | Запуск приложения |
| `make quality` | Проверка кода и форматирования Ruff |
| `make security` | Статический анализ безопасности Bandit |
| `make test` | Выполнение тестов с отчётами и проверкой покрытия |
| `make migrate` | Обновление схемы выбранной БД |
| `make backup` / `make restore` | Создание резервной копии и восстановление |
| `make verify` | Последовательное выполнение полного набора проверок |

Эта таблица описывает созданный интерфейс управления проектом. Фактически
выполненные проверки и их результаты приведены ниже.

## 2. Реализация комиссии аукциона

В форму создания аукциона добавлено поле комиссии в процентах от 0 до 100
с шагом 0,01. В API ставка представлена целым числом `commission_bps`:
100 базисных пунктов соответствуют 1%, 500 — 5%. Значение по умолчанию равно
нулю, поэтому сохранена совместимость со старыми запросами.

Расчёт реализован в целых копейках с округлением HALF_UP:

```python
(price_kopecks * rate_bps + 5000) // 10000
```

Например, при цене 150,25 руб. и ставке 5% комиссия составляет 7,51 руб.,
а сумма продавцу — 142,74 руб. Использование целых чисел исключило погрешности
двоичного представления дробных денежных сумм.

Комиссия сохраняется в записи продажи в одной транзакции с переводом лота
в статус SOLD. В ответ продажи добавлены `commission` и `seller_proceeds`,
а в отчёт — комиссионная выручка и сумма продавцам. Исторический результат
рассчитывается по сохранённым значениям: изменение ставки аукциона не меняет
комиссию уже состоявшейся продажи. Для старых продаж сохранена нулевая комиссия.

Автоматическими тестами проверены расчёт, округление, граничные значения,
сохранение результата и ответы API. Недопустимая ставка и дробное значение
`commission_bps` отклоняются с кодом 422.

## 3. Версионирование и миграции базы данных

Для последовательного изменения существующей схемы подключён Alembic.
Созданы три миграции:

| Ревизия | Выполненное изменение | Сохранение существующих данных |
| --- | --- | --- |
| 001 | Зафиксирована базовая схема из семи таблиц v0.1.1 | Старая схема принимается после проверки таблиц и внешних ключей |
| 002 | Добавлено поле `auctions.commission_bps` с DEFAULT 0 и CHECK 0..10000 | Старые аукционы получают нулевую ставку |
| 003 | Добавлено поле `sales.commission_kopecks` с DEFAULT 0 и ограничением от 0 до цены продажи | Старые продажи сохраняются без пересчёта |

Файлы миграций размещены в `migrations/versions`, текущая ревизия записывается
в таблице `alembic_version`. Исходная схема закреплена в
`migrations/baseline.sql`. Файл `schema.sql` оставлен как описание актуальной
предметной схемы.

Добавлена команда `make migrate`, вызывающая `python -m app.migrate`.
Обёртка выбирает файл через `DATABASE_PATH`, проверяет старую схему и управляет
транзакцией. Такой подход позволяет добавлять поля в существующие таблицы
и учитывать выполненные изменения; одного `CREATE TABLE IF NOT EXISTS`
для обновления существующих таблиц недостаточно.

Изменения схемы и запись ревизии объединены явной транзакцией
`BEGIN IMMEDIATE`. При ошибке выполняется откат. Неизвестная схема без версии
отклоняется вместо автоматического присвоения номера миграции.
SQLAlchemy используется в механизме Alembic; приложение продолжает работать
через `sqlite3` и явные SQL-запросы.

В составе выполненного `make verify` проверены:

- создание новой БД и последовательность 001 → 002 → 003;
- применение следующих миграций к уже заполненной БД;
- обновление исходной схемы v0.1.1 с сохранением значений во всех семи таблицах;
- сохранение хеша пароля, сессии и цены продажи;
- повторное применение миграций без изменения данных;
- отказ при неизвестной схеме и откат ошибки после `ALTER TABLE`.

Для отдельного запуска этих тестов добавлена цель `make migration-check`.
Обратное удаление финансовых полей запрещено; возврат к прежнему состоянию
предусмотрен через проверенную копию и совместимую версию приложения.

Также доработана проверка готовности `/ready`: она проверяет ревизию и
необходимые таблицы и поля. При потере файла БД во время работы возвращается
503 без создания пустой базы. Для существующей БД обновление схемы выполняется
явно через `make migrate`; при первом запуске с отсутствующим файлом создаётся
актуальная схема.

## 4. Резервное копирование и восстановление

Для резервного копирования реализована команда `make backup` на основе
`sqlite3.Connection.backup()`. Этот механизм создаёт согласованный снимок,
включая зафиксированные изменения в WAL. Простое копирование основного файла
работающей SQLite могло бы пропустить данные, находящиеся в журнале.

Добавлены проверки `integrity_check`, `foreign_key_check` и прикладной схемы.
Копии создаются с правами 0600, исключены из Git и не перезаписываются
неявно. Реализованы локальные копии без шифрования, внешнего хранилища
и автоматического расписания.

Восстановление реализовано командой `make restore`. Для него требуется
`APP_STOPPED=1`, а для замены существующего файла — дополнительно
`RESTORE_REPLACE=1`. Первый параметр фиксирует подтверждение оператора
об остановке приложения; автоматический поиск процессов не выполняется.
Наличие файлов `-wal`, `-shm` или `-journal` блокирует замену цели.

Перед заменой прежнее содержимое целевого файла сохраняется рядом под именем
`<имя>.before-restore-<суффикс>` с правами 0600. Повреждённая резервная копия
не перезаписывает целевую БД. Если сама цель была повреждена, сохранённый файл
содержит её прежние байты и не считается гарантированно исправной копией.

Для проверки полного цикла выполнена команда:

```bash
make backup-demo
```

Сценарий создал временную БД и добавил продавца. Далее были вызваны настоящие
команды `make backup` и `make restore`: между ними запись намеренно удалена
SQL-командой. После восстановления проверено количество записей и исходное
имя продавца. Получен следующий результат:

```text
After deliberate deletion: 0 sellers
Restoration verified: 1 seller, original name preserved
```

Таким образом, подтверждено восстановление исходной записи после удаления.
В составе общего тестового прогона дополнительно проверены восстановление
после UPDATE и DELETE, создание нового файла, работа с WAL, копия старой
схемы, повреждённый и отсутствующий источник, запрет неявной перезаписи
и сохранение прежнего состояния цели. Для отдельного запуска этих тестов
добавлена команда `make backup-check`.

## 5. Автоматические проверки и результаты

Для общей проверки проекта выполнена команда:

```bash
make verify
```

В ней объединены последовательные проверки зависимостей, качества кода,
безопасности, тестового покрытия и контрольных мутаций. При ошибке дальнейшее
выполнение прекращается. Последовательность сохраняется и при `make -j`.

| Проверка | Назначение | Фактический результат |
| --- | --- | --- |
| `pip check` | Совместимость установленных зависимостей | Нарушений нет |
| Ruff check / format | Ошибки Python, импорты и форматирование | Проверки пройдены; 24 Python-файла соответствуют форматированию |
| Bandit | Статический анализ `app` и `migrations` | 0 замечаний, без исключений |
| pytest | Unit-, API-, БД-, миграционные, backup/restore- и CLI-тесты | 74 passed, 0 failed, 0 errors, 0 skipped |
| Покрытие строк и ветвей совместно | Порог 85% | 95,31% в итоговом локальном прогоне |
| Покрытие строк отдельно | Исполнение строк кода | 604/621 = 97,26% |
| Покрытие ветвей отдельно | Исполнение ветвей условий | 108/126 = 85,71% |
| Матрица функциональных требований | Порог 40% | 13/14 = 92,86% |
| Контрольные мутации | Обнаружение намеренных ошибок | 3 из 3 обнаружены |

Повторный полный прогон после чистой установки также завершился успешно:
74 теста, совместное покрытие 94,78%. Разница покрытия связана с чтением
переменных окружения при импорте приложения; в обоих окружениях порог 85%
пройден без его изменения.

Настроено создание отчётов в каталоге `reports/`: JUnit XML, XML и HTML
покрытия, Bandit JSON, `functional-coverage.json` и `mutations.json`.
Результаты прогона также зафиксированы в [verification-lr3.md](verification-lr3.md).

Для тестов использованы отдельные временные БД через `tmp_path` и явные
значения `COOKIE_SECURE=false`, `SESSION_TTL_HOURS=8`. Рабочие `.env` и БД
не изменялись. Миграции и восстановление проверялись внутри общего pytest
без повторного запуска отдельными этапами. Пропуски и xfail блокируют проверку.

Ruff охватывает приложение, тесты, миграции и проверочные скрипты. Bandit
анализирует исполняемый код приложения и миграций стандартным набором правил.
Проверка Bandit является статическим анализом кода; аудит уязвимостей
зависимостей в неё не включён.

## 6. Проверка бизнес-правил и качества тестов

Unit-тестами изолированно проверены финансовая функция, округление, граничные
цены, валидация и парольные хеши. Интеграционные тесты через TestClient
и настоящую SQLite проверили совместную работу API, транзакций и базы данных.
Для конкурентной продажи использованы два соединения: одна операция
завершается успешно, вторая получает `LOT_ALREADY_SOLD`.

В `tests/functional-coverage.json` создана матрица FR-01..FR-14. Покрытие
требований рассчитывается по успешно выполненным тестам. FR-11 не засчитано:
полный сценарий в настоящем браузере не автоматизирован. Проверки HTML
и статических файлов не заменяют браузерный E2E-тест. Подтверждение FR-13
ограничено проверенными маршрутами и схемой cookie.

Дополнительно в составе `make verify` выполнены три контрольные мутации
во временных копиях проекта:

| Намеренное изменение | Результат |
| --- | --- |
| Удалён запрет продажи ниже стартовой цены | 1 падение assertion |
| Сравнение `<` заменено на `<=`, запрещая продажу ровно по стартовой цене | 2 падения assertion |
| Удалено округление HALF_UP при расчёте комиссии | 2 падения assertion |

Перед внесением каждой мутации выбранные тесты успешно прошли на исходном
коде. После изменения получены именно падения проверяемых утверждений
с кодом pytest 1, без ошибок импорта и подготовки. Рабочие исходники
при этом не изменялись. Для отдельного запуска добавлена цель
`make mutation-check`.

Эти результаты подтвердили, что тесты обнаруживают три выбранные ошибки
бизнес-логики. Процент покрытия сам по себе не доказывает отсутствие ошибок,
поэтому он дополнен матрицей требований и контрольными мутациями.
Исчерпывающее мутационное тестирование всего приложения не проводилось.

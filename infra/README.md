# Настройка окружений

Управляющий узел – `auction-test`. Ansible Core 2.22.0 и ansible-lint 26.11.0
работают в отдельном окружении Python 3.13.18. Целевые узлы – Debian 12,
на целевых узлах используется системный Python 3.11.

| Окружение | Узел | Адрес | Каталог приложения |
|---|---|---|---|
| test | auction-test | 10.0.2.6 | /opt/auction-test |
| staging | auction-staging | 10.0.2.7 | /opt/auction-staging |

`inventories/lab/hosts.yml` задаёт группы. Общие настройки находятся в
`group_vars/all/settings.yml`, ссылки на секреты – в `group_vars/all/secrets.yml`,
параметры окружений – в `group_vars/test.yml` и `staging.yml`, адреса узлов –
в `host_vars`. Роли `baseline` и `application` применяются к обоим окружениям.
Существующий мониторинг staging продолжает работать отдельно.

## Первый запуск

Начальные условия: установлен Debian 12, есть сетевой доступ, SSH-сервер,
учётная запись для начального входа и проверенный публичный ключ узла в
`~/.ssh/known_hosts`. При клонировании ВМ нужны разные MAC, machine-id и ключи
SSH-сервера. Эти действия относятся к созданию ВМ, адреса выдаются DHCP.

В `files/` находятся только публичные ключи. При переносе стенда требуется
заменить публичные ключи администратора, управляющего узла и развёртывания.
Закрытые ключи остаются вне репозитория. Если Ansible ещё отсутствует,
установить инструменты командой `sudo sh infra/setup-controller.sh` на
управляющей машине с учётной записью `auction-admin`.

С подготовленного управляющего узла:

```bash
cd infra
# Начальный вход root разрешён только на свежем узле. Пароль запрашивается,
# если добавлен --ask-pass; хранить пароль в inventory запрещено.
ansible-playbook bootstrap.yml -e ansible_user=root --limit auction-staging
ansible -m ping auction-staging
ansible-playbook site.yml
```

Проверка входа административным ключом выполняется до отключения root и
парольного SSH. `bootstrap.yml` устанавливает Python и sudo при отсутствии,
создаёт административную учётную запись и ключевой доступ.
Рабочий `site.yml` требует вход через `auction-admin` и настраивает остальное.
Первичная регистрация Tailscale требует подтверждения владельца сети:

```bash
sudo tailscale up --hostname="$(hostname)" --accept-dns=false
tailscale status
```

На готовых узлах повторная авторизация Tailscale не выполняется.

## Применение и проверка

Из корня репозитория:

```bash
make infra-check
make infra-apply
make infra-apply LIMIT=auction-test
```

Роль `application` использует существующие `scripts/deploy.py` и
`scripts/release_check.py`: принимает образ с заданной ревизией, применяет
миграции к копии БД и проверяет продажу, комиссию и закрытие аукциона.
Окружения имеют отдельные пароли, каталоги и Docker volumes. После каждого
применения проверяются `/health`, `/ready`, ревизия `/version`, вход оператора,
доступ к профилю и выход. Остановленный контейнер запускается повторно.
Изменение активной конфигурации приводит к приёмке нового экземпляра через
тот же процесс развёртывания с сохранением принятой ревизии. Параметр
`application_revision` задаёт начальную версию для чистого узла. На уже
работающем узле Ansible сохраняет версию, принятую CD, даже если начальная
версия inventory отличается. Для намеренной смены версии через Ansible
нужно явно включить `application_upgrade` и указать полный SHA проверенного
опубликованного образа:

```bash
cd infra
ansible-playbook site.yml --limit auction-test \
  -e '{"application_upgrade":true,"application_revision":"<full commit SHA>"}'
```

Обычный `make infra-apply` не включает обновление версии.

Повторное применение должно завершаться с `changed=0`. Для проверки исправления
изменённой конфигурации на test:

```bash
sudo sh -c 'printf "ENVIRONMENT=broken\n" > /etc/auction/environment'
sudo chmod 777 /opt/auction-test
make infra-apply LIMIT=auction-test
cat /etc/auction/environment
stat -c '%a %U %G' /opt/auction-test
make infra-apply LIMIT=auction-test
```

Ожидаемый результат – `ENVIRONMENT=test`, права `700 auction-deploy auction-deploy`,
успешные проверки приложения и отсутствие изменений при следующем запуске.

## Права, сеть и секреты

`auction-admin` имеет sudo для управления системой. `auction-deploy` входит
в группу Docker, необходимую существующему процессу доставки, но не в sudo.
Доступ к Docker фактически даёт управление узлом, поэтому ключ развёртывания
разрешён только доверенному процессу и установлен с SSH-параметром `restrict`.
Приложение работает от непривилегированного пользователя, с read-only корневой
ФС, без Linux capabilities и с ограничениями CPU и памяти.

Приложение слушает только `127.0.0.1:18000`, доступ выполняется через SSH-туннель.
Firewall допускает SSH из лабораторной подсети и Tailscale, UDP 41641 для
Tailscale, DHCP и ICMP. Метрики 9100 доступны только узлу мониторинга.
Правила IPv4 и IPv6 применяются отдельной цепочкой INPUT; Docker NAT и FORWARD
сохраняются. Службы включены в автозапуск. Роль не добавляет публичные порты.

Пароли автоматически создаются в `~/.config/auction-lab` управляющего узла:
каталог `0700`, файлы `0600`. Конфигурация приложения на целевом узле имеет
права `0600`. Задачи с паролями и cookie используют `no_log`, diff секретной
конфигурации отключён. Удаление файла пароля не меняет пароль в БД.
При утрате файла требуется восстановить сохранённую копию перед применением.

Для пакетов и файлов используются штатные модули Ansible. Единственный `raw`
нужен для установки Python до появления модульного транспорта. Команды Docker
вызываются через `argv` с проверкой текущего состояния. Firewall выполняет
короткий проверяемый скрипт, поскольку цепочки Docker должны сохраняться.
Обработчики перезапускают службы только при изменении управляемых файлов.

## Автоматическая приёмка

Workflow `Infrastructure` вызывается основным CI и запускает проверку `infra-check`:
syntax-check, production-профиль ansible-lint и применение настоящих ролей
к двум временным Debian-ВМ с systemd и Docker. Затем проверяются `changed=0`,
исправление конфигурации и прав, запуск остановленного контейнера и ещё один
повтор без изменений. Дополнительный прогон меняет начальную ревизию на
несуществующую и требует сохранить принятые релизы обоих узлов с `changed=0`.
Результаты сохраняются в `reports/infra`.

Для проверки запускаются две QEMU-ВМ на официальном cloud-образе Debian 12.
Образ проверяется по опубликованной SHA512-сумме. Обе ВМ имеют отдельные диски
и сеть QEMU с перенаправлением SSH только на loopback runner. Проверка не получает
секреты рабочих ВМ или Tailscale; ключи и пароли создаются на время запуска,
процессы ВМ останавливаются в `finally`. Доступ к `/dev/kvm` закреплён правилом
udev только для группы текущего runner. Завершение QEMU обнаруживается сразу;
причина остаётся в журнале соответствующей ВМ. Обработка такого сбоя и ожидание
готовности дополнительно проверяются отдельными тестами.

`infra/`, роли, шаблоны, ссылки на секреты, workflow и проверки защищены
CODEOWNERS и `critical-review`. Требуется согласование другого владельца кода
на актуальный SHA. Изменение после approval требует нового согласования.
Уже обязательный `ci-gate` зависит от результата инфраструктурного workflow и
не проходит при ошибке или пропуске проверки. Отдельное изменение настроек
защиты main не требуется. Обход защиты, прямой push и отключение проверок для
принятия изменения запрещены.
